# Tiflogram intermittent patch reliability report

## Executive diagnosis

The intermittent behavior was caused by three independent assumptions in the original patches rather than by a single Telegram download failure.

| Feature | Root cause | Corrective change |
|---|---|---|
| Completion sound | The patch searched transient `downloadingFiles` and `recentDownloadingFiles` lists during the completion callback and matched only `MessageObject.getDocument()`. Telegram photos and some HTTP media do not satisfy that document-only test, while the lists can already have moved by the time `fileLoaded` is delivered. | Play at the common successful-completion branch for `fileLoaded` and `httpFileDidLoad`, independent of attachment class, with a short filename debounce to suppress duplicate event variants. |
| Leading download percentage | The patch announced from `RadialProgress2.setProgress()` only when the renderer parent itself reported accessibility focus. Telegram uses `RadialProgress2` in several contexts, and ChatMessageCell exposes its message through a virtual accessibility host; the renderer parent is therefore not a reliable proxy for the focused TalkBack node. The description filter also excluded audio and other attachment types. | Track progress in `ChatMessageCell.onProgressDownload()`, refresh its virtual host node once per changed percentage, and prepend the percentage for every attachment whose message observer receives progress. |
| Translation | Forcing `TranslateController` into `TranslateAlert2.alternativeTranslate()` covered only the normal `pushToTranslate()` branch. The server-disabled fallback was separate, and the bundled `TiflogramTranslate` helper was not actually called. | Route both alternative and fallback callbacks through `TiflogramTranslate.translateWithRateLimit()`, using the same implementation and callback shape. |

## Upstream path confirmation

In the pinned Telegram revision, `DownloadController.didReceivedNotification()` receives both `fileLoaded` and `httpFileDidLoad` and then processes the filename, observers, message associations, and completion state. The former patch attempted to infer user intent from lists that are updated around the same callback. `ChatMessageCell` receives per-file progress through `onProgressDownload()`, while its accessibility text is generated by `MessageAccessibilityNodeProvider` under `HOST_VIEW_ID`. The patched implementation aligns with these actual ownership boundaries.

The upstream translation controller batches text in `pushToTranslate()`. Its alternative path and its `TRANSLATIONS_DISABLED_ALT` fallback were two separate call sites. The new patch covers both call sites and preserves the existing callback behavior. The public translator endpoint remains network-dependent; no client-side translation engine can guarantee results when the endpoint is unavailable or rate-limits the request.

## Validation

A fresh checkout of the pinned Telegram revision was patched from scratch. The revised scripts applied successfully, Python patch scripts compiled, `git diff --check` passed, Java brace-balance sanity checks passed for all modified classes, both translation call sites resolve to `TiflogramTranslate`, and the previous document-only/list-timing progress and sound logic is absent from the patched classes.

A complete Android release build was not run inside the sandbox because the repository intentionally builds the Telegram source only inside GitHub Actions. The workflow now executes `fix_reliable_feedback.py` immediately after `fix_accessibility.py`, so the post-accessibility transformation is applied in the correct order.
